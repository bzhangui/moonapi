# 初审整改的可运行反例

以下为本项目自建回环 HTTP 服务注入的合成缺陷，不是外部真实用户试点。执行 `npm run build && npm run demo:behavior`。正常对照与缺陷服务使用相同描述和模型，不靠删除响应契约获得通过。

| 案例 | 旧式契约检查为何不足 | 新机制与实际结果 |
|---|---|---|
| 更新接口只返回新值、不持久化 | PUT 返回 200、合法 id/name；随后 GET 也返回 200、合法字符串，schema 都符合 | readback 的 persisted_name 断言发现仍为 first；8 步缩减到 create → update → readback 三步，保留真实 ID 依赖和 updated 前提 |
| DELETE 返回 204 但未删除 | DELETE 自身状态合法 | 删除后再次读取期望 404，实际 200；8 步缩减到 4 步 |
| 重复取消订单两次返还库存 | 两次取消均返回 200/cancelled，库存也是合法整数，响应契约都通过 | 捕获 original_stock；预订 2 件后取消两次，末尾库存与捕获基准不等；6 步缩减到 5 步，保留基准读取、预订、两次取消和末尾读取 |

健康 CRUD 与健康订单服务均完整通过。更新缺陷原路径实际重置 13 次、订单缺陷重置 6 次（当前示例预算/候选顺序下），最终见证再次从干净状态重放。次数不是固定算法承诺，改预算/模型可能变化。

自动回归另外覆盖：缺失返回值依赖、错误转换顺序、未授权写/重置/重复写、重置失败/超时、不稳定失败、未知后续 operationId、只规划不写入，以及真实 CLI 的退出码和不含正文的摘要。公开示例输入都是合成的；完整运行报告与最小复现保存在 .local/reports，不推送。

这些案例证明有限范围的独立行为检查与缩减已经运行，不证明业务正确性、安全性或完整 OpenAPI 标准支持。最终是否满足初审/验收由赛事方决定。
